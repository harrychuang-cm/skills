Install the Component Coverage Analyzer — a Storybook Tools page where developers submit UI images / PRD text, an AI skill analyzes them against the project's component catalog, and developers review the resulting coverage report (可直接使用 / 需擴充 variant / 缺少需新建) before implementation.

## How the installed system works

```
Storybook Tools page (React UI, template)          ← developer submits requests, reviews reports
  ↕ fetch /__component-coverage/*                  ← dev API (vite plugin, template)
outputs/component-coverage/requests/<id>/          ← request.json + uploaded images (NOT committed)
outputs/component-coverage/reports/<id>.json       ← coverage reports (committed, review state included)
src/storybook/componentCatalog.ts                  ← per-project catalog (GENERATED by this skill)
src/storybook/component-coverage/
  compositionPreviewRegistry.tsx                  ← trusted project-owned real-component fixtures
.agents/skills/component-coverage-analyze          ← shared project skill for Cursor and Codex
.claude/skills/component-coverage-analyze          ← byte-identical Claude Code mirror
.agents/skills/component-coverage-implement        ← shared implementation skill for Cursor and Codex
.claude/skills/component-coverage-implement        ← byte-identical Claude Code mirror
```

Path contracts, skill source-to-target mappings, and expected skill hashes live in `template/TEMPLATE_MANIFEST.json`; runtime paths are mirrored in code (`coverageApi.ts` ↔ `vite-plugin.mjs` ↔ `.storybook/main.ts`). The report/review data contract's single source of truth is `src/storybook/component-coverage/coverageTypes.ts`.

## Two responsibilities, strictly separated

1. **Deterministic copy** — template files are copied VERBATIM. Do not rewrite, reformat, or "improve" them. Only the files listed under *Permitted adaptations* may be modified, and only in the ways listed.
2. **AI binding** — everything project-specific is generated or wired by you: the component catalog, trusted composition preview renderers, the `main.ts` wiring, the accent and preview-surface tokens, the story-entry import, and the verification run.

## Preconditions (check before touching anything)

- The target is a Storybook project using the **Vite builder** (`@storybook/react-vite` framework, or another Vite-based React setup). The dev API is a Vite `configureServer` middleware — it cannot work on the Webpack builder. If the project is not Vite-based React Storybook, STOP and tell the user why.
- The target has reusable components with stories. If it has none, warn the user that coverage analysis needs a component library to match against, and ask whether to proceed (the tool will render, but every block would be "missing").
- Locate the template: the `template/` directory next to this SKILL.md.
- If `outputs/component-coverage/TEMPLATE_MANIFEST.json` already exists in the target, this is an **update**, not a fresh install — jump to *Update mode*.

## Install flow

1. **Copy the template verbatim** (paths are target-repo-relative, identical to the template layout):

   - `src/storybook/component-coverage/` — all 10 files
   - `src/stories/tools/ComponentCoverageAnalyzer.stories.tsx`
   - `scripts/component-coverage/vite-plugin.mjs` + `vite-plugin.d.mts`
   - `scripts/check-component-coverage-reports.mjs`, `scripts/check-component-catalog.mjs`, `scripts/check-component-coverage-agent-skills.mjs`, `scripts/check-component-coverage-preview-contract.mjs`
   - `template/skills/component-coverage-analyze/` → each target declared by `installTargets`: shared `.agents/skills/` plus the `.claude/skills/` mirror
   - `template/skills/component-coverage-implement/` → the same shared `.agents/skills/` plus `.claude/skills/` mirror pattern
   - `TEMPLATE_MANIFEST.json` → `outputs/component-coverage/TEMPLATE_MANIFEST.json`

   Copy each upstream skill source separately to every target declared for it. Do not create per-agent source variants inside this template; the installed checker verifies every destination against the manifest's SHA-256 hash. Cursor and Codex both discover the shared `.agents/skills/` copy, while Claude Code uses `.claude/skills/`; do not add a redundant `.cursor/skills/` copy.

   If the target's stories live somewhere other than `src/` (check `stories:` globs in `.storybook/main.*`), keep the template's internal layout intact and place the whole `src/…` subtree at the equivalent covered location, keeping the relative structure (`storybook/component-coverage` next to `storybook/componentCatalog.ts`, story entry under a `stories/tools/` folder the globs cover).

2. **Permitted adaptations** (the ONLY template edits allowed):

   - `ComponentCoverageAnalyzer.stories.tsx`: change the `@storybook/react-vite` import to whatever module the project's existing stories import `Meta`/`StoryObj` from.
   - `compositionPreviewRegistry.tsx`: add direct imports for target-project components that can render with deterministic, side-effect-free fixture props. Register zero-argument renderers by `ComponentCatalogId`. Keep the empty scaffold for components that cannot be rendered safely; the preview will show a documentation fallback. Never read renderer props, imports, children, CSS, or executable content from a report.
   - `component-coverage.css`, `--cca-accent` (marked "Install binding"): point it at the project's primary color token with the current hex as fallback, e.g. `var(--their-primary-token, #e8590c)`. Keep the plain hex if no token system exists.
   - `component-coverage.css`, `--cca-preview-bg` (marked "Install binding"): point it at the target product's normal page/surface background token. Keep `var(--cca-bg)` when the product has no suitable token.
   - `component-coverage.css`, light-theme selector (marked "Install binding"): replace `:root[data-cca-theme="light"]` with the attribute/class the project's Storybook theme switcher actually sets. Leave as-is when there is no switcher (tool stays dark).

3. **Generate the component catalog** — the core binding step. Read `references/catalog-authoring.md` first, then:

   - Inventory the project's reusable components: story files, component sources, any existing component docs.
   - Write `src/storybook/componentCatalog.ts` starting from `componentCatalog.template.ts` (then delete the `.template.ts` copy from the target — the target keeps only the real catalog). Every entry needs the real `storyTitle` (copied from the story file or its autotitle) and a real, existing `componentPath`.
   - Scope: reusable library components only — not screens/pages/prototype compositions.
   - Present the generated catalog to the user for review before finishing; catalog quality decides analysis quality.

4. **Wire `.storybook/main.*`**:

   - Import and register the dev API plugin inside `viteFinal` (create `viteFinal` if absent):
     ```ts
     import { createComponentCoverageApiPlugin } from "../scripts/component-coverage/vite-plugin.mjs";
     // in viteFinal:
     plugins.push(createComponentCoverageApiPlugin());
     ```
   - Add to `staticDirs`: `{ from: "../outputs/component-coverage", to: "/component-coverage" }` (adjust `from` to be correct relative to the `.storybook` dir).

5. **Create the data directory**: `outputs/component-coverage/reports/.gitkeep`, and add a `.gitignore` rule for `outputs/component-coverage/requests/` (requests hold local working images — never committed; reports ARE committed).

6. **Wire validation scripts**:

   - Add the required aliases `"check:coverage-reports": "node scripts/check-component-coverage-reports.mjs"`, `"check:coverage-agent-skills": "node scripts/check-component-coverage-agent-skills.mjs"`, and `"check:coverage-preview": "node scripts/check-component-coverage-preview-contract.mjs"`. Agent handoff prompts call the underlying Node scripts directly, so they remain package-manager-neutral; the aliases keep the checks discoverable to developers and aggregate scripts.
   - Optional alias (ask or follow project convention): `"check:component-catalog": "node scripts/check-component-catalog.mjs"`.
   - Hook all three required aliases into an existing aggregate `check` script. When the optional alias is added, hook it into the same aggregate script as well.

## Verify (all must pass before reporting success)

1. `node scripts/check-component-catalog.mjs` passes.
2. `node scripts/check-component-coverage-reports.mjs` passes.
3. `node scripts/check-component-coverage-agent-skills.mjs` passes, confirming both analyze and implement skills match their manifest SHA-256 hashes across the shared `.agents` copy and Claude Code mirror.
4. `node scripts/check-component-coverage-preview-contract.mjs` passes, confirming the installed preview, selected-block UI Reference evidence crop and fallback, Inspector, selection clearing, report disclosure, and new-window documentation affordances remain intact after adaptation.
5. The project's typecheck (or `tsc --noEmit`) passes with the new files.
6. Storybook dev starts; `GET http://localhost:<port>/__component-coverage/state` returns JSON (`{"requests":[],"reports":[]}` on a fresh install).
7. The `Tools/Component Coverage Analyzer` page renders with the intake form (submit stays disabled until an image or PRD text is provided), and the Storybook index contains no redundant `Review Preview` story.
8. A production build (`storybook build`) succeeds — confirms the static-mode fallback bundle.

Report to the user: files installed, catalog entry count, adaptations made, and how to use the workflow (submit in the tool → copy the analysis prompt to Cursor, Claude Code, or Codex → review in the tool → copy the implementation prompt to the same agent). Both handoffs use agent-neutral prompts with a `.agents/skills/` fallback path, and both project skills are mirrored byte-for-byte for Claude Code.

## Update mode

When `outputs/component-coverage/TEMPLATE_MANIFEST.json` exists in the target:

1. Compare its `version` with the template's. Same version → nothing to do unless the user asks for a reinstall.
2. Before overwriting the old manifest, compare its `installTargets` with the new manifest. For every retired managed target, compare it with the old first target for the same source; delete it only when byte-identical, otherwise show the local diff and ask before removal. The `0.3.x` → `0.4.x` migration retires `.cursor/skills/component-coverage-analyze/SKILL.md` because Cursor now uses the shared `.agents/skills/` copy. The `0.4.x` → `0.5.x` migration adds the optional composition contract and the adaptable trusted renderer registry; initialize that registry from the target's current catalog rather than copying fixtures from another project. The `0.5.x` → `0.6.x` migration extends the reusable review decision set to `approve`｜`use-existing` (developer overrides of the analyzer's exact-match pick, carried by `overrideComponentId`) and adds presentation-only 首選／候選 rank chips on multi-candidate match cards; no data migration is needed because existing reports remain contract-valid. The same release restyles the adaptable CSS baseline to a tiered action hierarchy (filled/tonal/ghost, outlines reserved for form fields), a 16/12/8/6px radius scale with surface-layered depth (--cca-surface-3), and uniform hover/focus-visible/disabled states; when updating, re-apply the target's accent token, preview background token, and theme selector bindings on top of the new baseline. The `0.6.x` → `0.7.x` migration adds the UI Reference switch, multi-image reference fallback, optional canvas selection with blank-canvas/Escape clearing, Inspector metadata plus a new-window Docs link, immediate draft override preview, and a visibly connected expanded report row with an open-state label and disclosure control. Preserve the target's trusted renderer registry and CSS install bindings, copy the new preview contract checker, and add its required package alias; no report data migration is required. The `0.7.0` → `0.7.1` migration adds the selected-block UI Reference evidence crop to the Inspector by reusing `CoverageBlock.evidenceRegion` and matching request images. Draft or saved component overrides update metadata and Docs without replacing the crop; selecting another block replaces it, while missing or failed source evidence degrades to `無可用 UI Reference 截圖`. No report data migration is required.
3. Diff each `files.verbatim` entry between template and its direct target. Entries that are keys in `installTargets` have no direct `skills/…` target: compare that template source with every declared target path and overwrite those mapped targets only. If a target copy was locally modified, show the user the diff being discarded and get confirmation first.
4. Process every `files.adaptable` entry as an update baseline too. If an adaptable target does not exist yet, copy its template scaffold first (this is required for newly introduced files such as `compositionPreviewRegistry.tsx`). If it exists, preserve or merge only the bindings allowed under *Permitted adaptations*; do not blindly overwrite project-owned adaptations. Then re-apply the project's trusted preview renderers, accent token, preview background token, theme selector, and story import.
5. Ensure all three required validation aliases from the install flow exist; older installations may not have the preview contract alias.
6. NEVER touch `src/storybook/componentCatalog.ts` (project-owned), `outputs/component-coverage/requests/`, or existing reports.
7. Copy the new manifest over, run the agent-skill checker to confirm every installed skill target matches the new hashes, re-run the full *Verify* list, and summarize what changed.

## Guardrails

- Template files are vendored: no edits beyond the *Permitted adaptations*, ever — fixes belong upstream in this skill's `template/`.
- Keep one upstream source per component coverage skill in `template/skills/` and install it to every manifest target. Never maintain separate upstream agent variants.
- Recompute the matching `skillContentSha256` value whenever an upstream skill source changes. Hash UTF-8 text after normalizing CRLF to LF, matching `check-component-coverage-agent-skills.mjs`; the checker treats a stale hash as a failed installation.
- Use `.agents/skills/` as the shared Cursor/Codex location and `.claude/skills/` as the Claude Code mirror. Do not install duplicate `.cursor/skills/` copies.
- Never fabricate catalog entries for components that don't exist, and never let `storyTitle`/`componentPath` drift from reality — the check scripts and the analyze skill both depend on them.
- `coverageTypes.ts` is the data contract's single source of truth; the vite plugin, check script, and companion skills mirror it. If you change one, you must change them all — which is another reason not to change any of them during install.
- Keep analysis and implementation handoffs agent-neutral; do not add agent-specific slash commands or tool names.
- Keep `compositionPreviewRegistry.tsx` project-owned and deterministic. Reports may select a catalog id but must never supply renderer props, imports, JSX, styles, or executable content.
- Do not commit anything in the target project unless the user asks; list the created/modified files instead.
