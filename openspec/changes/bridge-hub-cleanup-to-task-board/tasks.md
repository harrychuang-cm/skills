## 4. Hub Coordinator：派工模式

- [x] 4.1 Coordinator resolves a local dispatch binding and falls back to standalone 與 Dispatch binding is local, untracked, and never distributed：對應 design 的「綁定設定放在未追蹤的本機檔案，缺席即回到 standalone」決策——新增 task-board-binding.mjs 解析環境變數優先、.design-automation/task-board.json 次之的綁定，三個必要欄位缺一即視為未綁定，專案 slug 預設與 worker 的 slugForRoot 規則一致，錯誤只帶穩定錯誤碼且不含 URL 與 token；gitignore.fragment 新增該綁定檔路徑。驗證：新增模板端 node --test 案例涵蓋「環境變數覆寫檔案」「缺 token 視為未綁定」「slug 推導對照表」，並人工確認安裝後的 .gitignore 含該路徑。
- [x] 4.2 Bound Coordinator dispatches cleanup instead of analyzing locally：對應 design 的「派工模式以裝飾既有 core 的方式接上，不改 core 與 agent-runner」決策——新增 dispatch.mjs 提供派工版 scheduleTask（落地 runtime input、呼叫控制平面建卡、任務留在 queued 並掛上派工區塊）與 task-board-client.mjs 的 HTTP 客戶端；建卡失敗時任務 queued → blocked 並帶穩定派工失敗碼，已落地的 input.json 保留。standalone.mjs 依綁定結果注入，未綁定時注入路徑與今天完全相同。驗證：模板端測試斷言「綁定時不 spawn 任何子程序且 input.json 已存在」「建卡失敗落到 blocked」，並以 git diff 確認 core.mjs 與 agent-runner.mjs 未被修改。
- [x] 4.3 Dispatched task status advances from durable runtime evidence：對應 design 的「Hub 任務狀態機不變，改用調解（reconcile）推進」決策——裝飾層在 listTasks 與 taskDetail 之前調解 queued 且有派工區塊的任務：runtime 有合法 result.json 就走 queued → analyzing → plan-ready 並記錄 plan 與 genericRunId，驗證失敗走 → blocked，無 result 時查卡片狀態（NEEDS_ATTENTION → blocked，其餘維持 queued 並更新已知欄位），查詢失敗不改狀態也不讓讀取失敗。驗證：模板端測試涵蓋三條路徑，並斷言 TRANSITIONS 表未新增任何狀態。
- [x] 4.4 Plugin apply outcome is written back to the board：對應 design 的「看板欄位與 Hub 狀態的對齊，以及 Plugin apply 後的回寫」決策——completeTask 之後回報 applied、failTask 之後回報 failed（只帶穩定錯誤碼），回寫為盡力而為：失敗不改變 Plugin 回應與任務狀態，只輸出一行不含憑證的訊息。驗證：模板端測試斷言「控制平面不可達時 Plugin 仍收到成功完成回應且任務為 completed」，並以 hub-cards.test.ts 的 outcome 案例對上看板側行為。
- [x] 4.5 Dispatch mode never becomes an extraction queue：server.mjs 的 /healthz 在兩種設定下都回報 status ok、schemaVersion 1、extractionQueue false，並新增布林 dispatch 旗標；派工模式不新增任何端點、不維護待萃取集合，standalone 的 review 仍為 false。驗證：以 curl 對未綁定與已綁定的 Coordinator 各取一次 /healthz 比對欄位，並執行 node design-automation-hub-install/scripts/check-design-automation-hub-install.mjs --template --json 通過。
- [x] 4.6 Plugin workflow status explains dispatch state：ui.html 對帶派工區塊的任務顯示等待放行、等待領取、執行中、需要處理四種狀態，並在超過停滯門檻仍未被領取時明說「尚無機器領取」與「只有讀得到本專案 runtime 目錄的機器可領」；任務未到 completed 前不得呈現為已完成。驗證：以 grep 確認新增文案鍵存在於 ui.html 的 COPY 表，並在 Figma Desktop 以一個綁定專案人工確認四種狀態文案。
