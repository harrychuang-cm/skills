## Context

倉庫已有 `executive-presentation`（起草四頁提案、補找案例）。本次需求是「審查」：對任意來源的簡報稿，逐頁檢查標題是否為一個結論（觀點＋行動）、副標是否用理由補充、每頁是否有 1–3 個能佐證結論的證據。使用者明確表示規則會持續迭代，因此規則本身要能獨立於流程更新。工作樹目前乾淨，本次只新增此 skill、其 Codex 顯示資訊、README 對應段落與本 change 的 Spectra 文件。

## Goals / Non-Goals

**Goals:** 讓設計師把簡報稿丟進來就能得到逐頁、可直接照改的審查結果；讓規則迭代只需編輯一個檔案，且舊規則 ID 不變。

**Non-Goals:** 不產檔、不審視覺、不建立案例資料庫、不新增工具依賴、不更新使用者安裝副本（另依授權處理）、不提交或推送。

## Decisions

- **流程與規則分離。** `SKILL.md` 只寫輸入處理、審查步驟、報告產出、改寫原則與規則迭代方式；規則細節全部放在 `references/rules.md`，SKILL.md 每次執行都要求先讀取該檔。這樣新增或調整規則時不必重寫流程，也避免兩處規則不一致。
- **規則 ID 固定、來源可辨。** 規則分標題（T）、副標（S）、證據（E）、整體（D）四組，每條有 ID、通過條件、常見失敗與嚴重度。使用者提出的三條核心規則標為「使用者規則」，為了讓核心規則可判定而補的檢查標為「衍生規則」，方便使用者刪改。停用規則加標記，不重新編號；版本紀錄放檔尾。
- **證據以四要素加關聯與強度判定。** 主體（哪個產品／團隊／自家數據）、做法（做了什麼功能）、成果（成長或結果，含數字、期間）、來源；另判定是否直接支持該頁結論，並標示已驗證成效／做法參考／預期待驗證。沿用 `executive-presentation` 的證據用語，讓兩個 skill 的輸出可以互相接續。
- **改寫建議不捏造。** 標題、副標可直接改寫；證據缺口一律用「待補」標記寫明需要什麼，不填造數字或案例。使用者要求補找時，使用目前可用且已授權的查詢能力，讀取原文後才引用。
- **預設輸出是報告，不是改好的簡報。** 使用者明確要求時才輸出整份改寫稿或依規則起草；起草時可先用 `executive-presentation` 產稿再用本 skill 審查，流程只跑一次。
- **不寫腳本。** 判定需要理解語意（標題是否為結論、證據是否支持結論），不適合以正規表達式自動化；本次不提供 scripts，避免假自動化。

## Implementation Contract

- 輸入：Markdown、純文字大綱、貼上的逐頁文字；檔案或圖片依環境可用能力擷取文字，無法讀取時明說並請使用者提供文字版。分頁不明確時寫出假設的切法。
- 輸出：依 `references/review-report-template.md` 的結構，繁體中文；每頁至少有標題、副標、證據數、證據品質四項判定與依據引文；必改清單依優先順序；未檢查的項目與限制列在報告末尾。
- 嚴重度：必改（標題缺觀點或缺行動、零證據、證據與結論無關或疑似捏造）、建議（副標未給理由、證據缺數字或來源、超過 3 個證據）、可選（用字精簡）。
- 規則迭代：使用者提出新規則或修改時，更新 `rules.md`（新增 ID、調整條文、版本號、版本紀錄），向使用者複述規則內容確認；流程未變就不動 SKILL.md。
- 驗收：逐項人工審閱規格情境；執行 skill-creator quick_validate、openai.yaml YAML 解析與短說明長度檢查、共用安裝器 dry-run、Spectra validate／analyze、限定檔案的 git diff --check。

## Risks / Trade-offs

- 規則判定依賴語意理解，不同 agent 可能判定不一 → 每條規則寫明通過條件與常見失敗，並要求引用原文作為依據，讓使用者能核對。
- 規則檔越迭代越長 → 以 ID 分組、停用不刪除、版本紀錄在檔尾；SKILL.md 保持精簡。
- 審查時容易順手補造證據 → 明確禁止，缺口一律待補標記；補找時必須讀取原文。
