## ADDED Requirements

### Requirement: Injection site definition

The DataSource pattern section SHALL define what the replacement point is on native targets and name the available forms with their trade-offs: an environment or composition-local value, constructor injection into the view model, and a dependency-injection module registration. The implementation SHALL record which form it used and where, so the data-integration owner has a single named place to swap, and the implementation map's seams table SHALL carry that location.

#### Scenario: Seam recorded for hand-over

- **WHEN** the implementation wires a mock data source into a feature
- **THEN** the seams table names the interface, the mock implementation path, and the injection site, so the next stage swaps one registration rather than searching the feature

### Requirement: Fixture resource loading

The DataSource pattern section SHALL specify how the mock implementation loads the handoff's JSON fixtures on each platform, covering the bundle distinction on iOS between a package's own bundle and the application bundle, and the Android distinction between application assets and test-only resources. It SHALL state that choosing the wrong location produces either a runtime failure in the app or a mock that works only under test, and SHALL cross-reference the build membership rules.

#### Scenario: Fixtures loaded from a package

- **WHEN** the mock data source lives in a local package that declares the fixtures as resources
- **THEN** it loads them from that package's bundle rather than the application bundle

#### Scenario: Fixtures needed by the running app

- **WHEN** previews and the running app both drive their states from the fixtures
- **THEN** the fixtures are packaged where the app can read them at runtime, not only where tests can

### Requirement: Build membership and resources

The implementation workflow SHALL contain a section stating that on native targets a file existing is not the same as a file building. It SHALL cover: new source files needing target membership in the Xcode project; projects generated by a project generator requiring the generator's spec to change and the project to be regenerated, because direct edits to the generated project file are overwritten; resource declarations for package-held assets; and the Android distinction between assets, raw resources, and test resources.

#### Scenario: Project managed by a generator

- **WHEN** the repo contains a project-generator specification alongside the generated Xcode project
- **THEN** new files are added through the generator specification and the project is regenerated, instead of editing the generated project directly

#### Scenario: New source file in a plain Xcode project

- **WHEN** a new Swift file is created in a project not managed by a generator
- **THEN** its target membership is confirmed so the file compiles into the app rather than sitting outside the build

### Requirement: Contract semantics inform the seam

The DataSource pattern section SHALL require reading the handoff contract's semantics entries — pagination, sort and filter, freshness, mutation semantics, and error taxonomy — when designing the interface, so that the method shapes can carry them, and SHALL state that unresolved semantics are questions for the named contract owner rather than assumptions baked into the interface.

#### Scenario: Paginated list contract

- **WHEN** a fixture group's contract records cursor pagination
- **THEN** the interface method carries the cursor parameter and the mock honors it, instead of returning one fixed page that the real implementation cannot substitute for
