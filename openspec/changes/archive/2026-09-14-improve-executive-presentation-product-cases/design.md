## Context

現有 skill 的四頁結構、來源規則與產檔誠實性可延用。新增自動查證會影響何時搜尋、何時詢問素材，以及何時能把案例當成證據，因此需要先定義這些判斷。倉庫已有其他未提交修改，本次只改此 skill、其顯示資訊與 README 對應段落。

## Goals / Non-Goals

**Goals:** 讓 UIUX 設計師快速看懂提案價值、取得可分享案例，並辨識已知事實與仍需驗證的期待。

**Non-Goals:** 不新增工具依賴或固定服務、不實際產簡報、不更新使用者安裝副本、不提交或推送，不更動其他工作內容。

## Decisions

- 沿用四頁預設但改成產品問題與價值敘事。框架縮寫不出現在預設成品；保留來源、反證與責任時程，避免白話化同時削弱判斷品質。
- 缺口導向搜尋：先讀已有資料，必要時查可用內部文件或原始公開來源；預設一至兩個貼近問題的案例。充分覆蓋關鍵缺口，或一次有範圍的查詢加一次針對性調整仍無支持時，就交付限制與草稿。使用者要求深入研究時才擴大。
- 詢問素材與撰稿可同時進行。只在缺少可引用素材時問一次用途明確的問題；已有截圖、使用者拒絕或沒有資料時不重複問。若缺口會改變核心建議，草稿維持條件式建議。
- 每個案例同時交代可借鏡處及適用差異。畫面只支持做法存在；來源中的成效要保留原適用範圍，不能套用成本地成果。
- 指令仍集中在 SKILL.md；這些流程每次生成都會用到，不增加獨立參考文件或固定案例庫。

## Implementation Contract

- 內容介面：維持四頁繁體中文 Markdown，使用者指定的語言、頁數、格式及資料範圍優先；實際標題表達本頁結論。
- 案例內容：產品與情境、做法、與提案的關係、證據強度、來源及可用畫面狀態。只列與該案例有關的日期或版本，不補造資料。
- 查詢失敗：明示無法讀取的文件、欠缺的搜尋能力或未找到的證據；不虛報查證完成，也不因素材尚缺而停止所有撰稿。
- 驗收：逐項人工審閱規格案例，檢查白話、搜尋邊界、截圖與成效區分、拒絕補件及既有 ROI/空輸入規則。執行 skill-creator quick_validate、metadata YAML 解析、共用安裝器 dry-run、Spectra analyze/validate 與限定檔案 git diff --check。此輪不將規則審閱宣稱為各 agent 的實際生成驗收。
- 修改範圍：executive-presentation/SKILL.md、executive-presentation/agents/openai.yaml、README.md 的 executive-presentation 小節，以及本次 Spectra 規格與記錄。README 以修改前副本確認其他段落不變。

## Risks / Trade-offs

- 自動查詢會增加生成時間 → 只補關鍵缺口，先整理一至兩個案例，有停止條件。
- 公司資料權限及搜尋能力因環境而異 → 使用既有可用能力，無權限時詢問來源，不自行安裝或登入。
- 案例看似成功卻未量化 → 標為做法參考，並安排自己的驗證方式。
