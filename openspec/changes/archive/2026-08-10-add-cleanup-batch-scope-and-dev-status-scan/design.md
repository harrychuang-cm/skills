## Context

Design Automation Hub 的 Figma Plugin 由兩個檔案組成：沙箱側的 main.js（可存取畫布）與 iframe 側的 ui.html（可發網路請求）。兩者以 postMessage 溝通，整理設計稿的既有流程是：UI 送出擷取範圍請求 → main.js 讀取畫布上唯一的選取節點、遞迴建立快照並算出 SHA-256 雜湊 → UI 帶著快照與雜湊向 Coordinator 建立一筆 `figma-cleanup` 任務 → 代理產出整理提案 → 使用者確認後 UI 請 main.js 套用，套用前重新擷取快照比對雜湊，任何失敗都在該範圍內反向回滾。

限制單一選取的是擷取端的守門條件，而非後端資料模型：Coordinator 的建立任務端點本來就是一次一個範圍、一個雜湊，且多筆任務可並存。因此「一次處理多個 Section」的正解是在 Plugin 端建立多筆任務，而不是讓單筆任務承載多個範圍。

三個硬性約束限制實作空間：

1. main.js 必須維持 ES2018 語法，安裝檢查腳本會逐一斷言禁用箭頭函式、選擇性串連、空值合併、私有欄位與動態匯入，並以函式建構子驗證可解析。
2. Plugin manifest 使用 dynamic-page 文件存取模式，只有目前頁面保證已載入，跨頁遍歷需要額外載入所有頁面。
3. 首頁入口數量在 UI 端硬性截斷為三個，安裝檢查腳本會斷言此截斷存在，新功能不得新增第四個首頁入口。

## Goals / Non-Goals

**Goals:**

- 讓設計師一次選取多個範圍並一次建立多筆整理任務，免去逐個往返。
- 讓設計師以 Figma Dev Mode 的 Ready for dev 標記當作批次來源，不必回畫布手動點選。
- 完整保留既有套用安全鏈：每個範圍各自持有快照雜湊、套用前重新驗證、失敗時範圍內回滾。
- Coordinator 端零改動，既有已安裝專案只需更新 Plugin 檔案。

**Non-Goals:**

- 不新增批次建立任務的 Coordinator 端點，也不讓單筆任務承載多個範圍。
- 不接 Figma Webhook、不做 Plugin 關閉後的背景執行、不自動套用整理提案。
- 不掃描目前頁面以外的頁面。
- 不放寬單一範圍的 500 節點與 1MB 快照上限。
- 不改動元件覆核與流程狀態功能，也不新增首頁入口。

## Decisions

### 批次以多筆任務實作，不擴充任務資料模型

一批 N 個範圍等於 N 筆獨立的 `figma-cleanup` 任務，UI 依序逐筆呼叫既有的建立任務端點。

理由：快照雜湊、範圍內外判定、回滾邊界全都以單一根節點為前提，若讓一筆任務承載多個根節點，就必須重新定義「其中一棵樹被改動時另一棵要不要一起作廢」，等於重寫整條安全鏈。多筆任務則讓每個範圍各自失敗、各自重試、各自過期，語意清楚且後端零改動。

替代方案：新增一個接受多個範圍的批次端點。否決原因是它把跨範圍的部分失敗語意推進後端，而後端目前沒有任何跨任務交易概念。

冪等鍵沿用既有格式，其尾段本來就是該範圍的快照雜湊，不同範圍自然產生不同鍵，無須調整格式。

### 拒絕互相包含的選取組合

同一批內若有任一節點是另一節點的祖先或後代，整批擷取失敗並回報單一錯誤碼，不做部分接受。

理由：重疊範圍會讓兩份快照描述同一批圖層，先套用的那筆會使另一筆的雜湊失效，使用者看到的是「莫名其妙過期」而非清楚的錯誤。在擷取端直接擋掉，錯誤訊息可以明確指向原因。

替代方案：自動收斂成最外層節點。否決原因是它會靜默丟棄使用者明確選取的項目，使用者無從得知哪些範圍沒有被處理。

### Ready for dev 掃描只取最外層命中節點

掃描目前頁面時，一旦某節點命中 Ready for dev 就將其列為候選並停止往下遞迴。

理由：這自然保證候選清單內不會出現互相包含的組合，與上一條拒絕規則一致；且設計師標記父層 Section 為 Ready for dev 時，意圖就是整段一起處理，而非其中每個子 Frame 各自成案。

### Ready for dev 狀態以防禦性讀取取得

讀取節點狀態前先檢查該屬性是否存在且為物件，屬性不存在時一律視為未標記，而非拋出例外。掃描結果為空時，UI 顯示「目前頁面沒有標記為 Ready for dev 的範圍」，並保留手動選取路徑。

理由：Dev Mode 狀態屬性未必存在於所有節點型別與所有 Figma 版本，掃描失敗不應該讓整個整理功能不可用。手動選取始終是可用的後備路徑。

### 批次清單與單筆詳情分層呈現

整理設計稿頁面新增一層批次清單：每列顯示範圍名稱與任務狀態，點入後進入既有的單筆詳情視圖（整理提案、勾選項目、確認、套用）。批次只有一筆時直接進入詳情視圖。

理由：套用動作本質上是一次一個範圍的人工確認，強行做成批次確認會讓使用者在看不到細節的情況下一次授權多筆畫布修改，違反現有的零意外修改承諾。分層可以完整重用既有的提案與套用畫面，改動集中在清單與狀態管理。

### 批次上限固定為十個範圍

超過上限時整批擷取失敗並提示縮小選取。

理由：每個範圍的快照上限為 1MB，十筆即約 10MB 常駐於 iframe 記憶體，同時代理端也需要逐筆分析；固定上限讓資源用量可預測，也避免使用者一次框選整頁後才發現卡住。

## Implementation Contract

### 行為

- 在畫布選取一個以上受支援節點（Section、Frame、Component、Component Set）後執行擷取，Plugin 逐一建立快照，UI 顯示這批範圍的名稱與圖層數。
- 按下開始分析後，UI 依序為每個範圍建立一筆任務，並切換到批次清單畫面顯示各筆狀態。
- 執行 Ready for dev 掃描後，UI 列出目前頁面所有最外層 Ready for dev 節點作為候選，設計師勾選後可直接排入分析，不需回畫布重新選取。
- 進入任一筆任務後的提案檢視、勾選、確認、套用、回滾與錯誤呈現，與既有單筆流程完全一致。

### 訊息契約（UI 與沙箱之間）

擷取請求由 UI 送出，型別為 `capture-cleanup-scopes`，可選帶字串陣列 `nodeIds`；未帶或為空陣列時以目前頁面的選取為來源，帶值時以節點識別碼解析為來源（供掃描後勾選使用）。

擷取回覆型別為 `cleanup-scopes-result`，成功時 `ok` 為真並帶 `scopes` 陣列，每個元素包含 `scope`（含節點識別碼、型別、名稱、節點數）、`snapshot`、`inputSnapshotHash` 三個欄位，欄位形狀與既有單筆回覆一致；另帶 `rejected` 陣列，每個元素包含節點識別碼、名稱與錯誤碼。

掃描請求型別為 `scan-ready-for-dev`，回覆型別為 `ready-for-dev-scan-result`，成功時帶目前頁面名稱、`candidates` 陣列（每個元素含節點識別碼、型別、名稱）與布林 `truncated`。

套用相關訊息（重新驗證範圍、套用整理提案、聚焦節點）維持現有型別與欄位，不做任何變更。

### 失敗模式

整批層級失敗回覆 `ok` 為偽並帶單一錯誤碼，且不回傳任何範圍。三種情形：來源為空、選取組合互相包含、超過批次上限。既有的來源為空錯誤碼沿用；互相包含與超過上限各新增一個穩定錯誤碼。

單筆層級失敗不影響整批：節點型別不受支援、超過節點數或位元組上限、快照讀取失敗者進入 `rejected` 陣列，其餘範圍照常回傳。若全部範圍皆遭拒，則回覆 `ok` 為偽並以第一筆的錯誤碼作為整批錯誤碼。

建立任務時若其中一筆請求失敗，已成功建立的任務保留在清單中，失敗者以可重試狀態呈現，不回捲已建立的任務。

掃描無法取得狀態屬性時回傳空候選清單而非錯誤，UI 以「沒有候選」而非「失敗」呈現。

### 驗收條件

- 安裝檢查腳本新增斷言：沙箱程式碼不含既有的單一選取守門條件、含批次上限常數與最外層命中即停止遞迴的掃描邏輯；UI 含批次清單與 Ready for dev 候選的新增文案。
- 安裝檢查腳本既有的 ES2018 語法斷言與函式建構子解析驗證必須持續通過。
- 安裝檢查腳本既有的三個首頁入口斷言、專案中性文案斷言、零修改承諾文案斷言必須持續通過。
- 範本清單檔重新產生後，兩個 Plugin 檔案的雜湊與長度與實際檔案一致，範本驗證通過。
- 手動驗收：於 Figma Desktop 匯入 Plugin，選取兩個不重疊 Section 可建立兩筆任務；選取一個 Section 與其內部 Frame 時整批被拒並顯示重疊原因；將一個 Section 標為 Ready for dev 後掃描可將其列為候選。

### 範圍邊界

在範圍內：沙箱側的擷取與掃描邏輯、UI 側的批次狀態管理與清單呈現、安裝檢查腳本的新增斷言、範本清單檔重新產生。

在範圍外：Coordinator 的任何檔案、companion skill 的分析規則與整理結果契約、元件覆核與流程狀態功能、Plugin manifest 的權限與網域設定、首頁入口組成。

## Risks / Trade-offs

- [沙箱與 UI 訊息型別同時改名，若只更新其中一個檔案，整理功能會完全失效] → 兩個檔案在範本清單中皆為受管檔案，安裝與更新流程一併覆蓋；安裝檢查腳本新增斷言同時檢查兩側，任一側未更新即失敗。
- [一批多筆任務同時等待代理分析，設計師等待時間比單筆長] → 批次清單顯示各筆獨立狀態，先完成者可先進入套用，不需等待整批完成。
- [十個範圍的快照同時常駐 iframe 記憶體] → 以批次上限十筆作為上界；建立任務後不再保留原始快照於清單狀態，只保留範圍摘要與任務識別碼。
- [設計師先套用其中一筆後，另一筆的快照因共同祖先被改動而過期] → 重疊選取已在擷取端被拒，一般情況下互不影響；仍會過期的情形由既有的套用前重新驗證擋下，回報過期並要求重新分析，畫布不會被修改。
- [Dev Mode 狀態屬性在部分節點型別或版本上不存在] → 防禦性讀取，缺屬性視為未標記；手動選取路徑不受影響，功能可降級使用。
- [批次清單增加 UI 狀態複雜度，可能影響既有單筆流程] → 單筆時直接進入詳情視圖，既有畫面與互動路徑不變；提案、確認、套用三個畫面的算繪函式不做行為性修改。

## Migration Plan

1. 更新兩個 Plugin 檔案，重新產生範本清單檔。
2. 更新安裝檢查腳本斷言，於範本層執行檢查。
3. 既有已安裝專案透過既有的安裝更新流程取得新版 Plugin 檔案，Coordinator 不需重啟或重新設定。
4. 使用者在 Figma Desktop 重新載入 Plugin。
5. 回滾策略：兩個 Plugin 檔案與範本清單檔一併還原至前一版即可，因為 Coordinator 資料模型未變動，批次期間建立的任務在舊版 Plugin 下仍可逐筆檢視與套用。

## Open Questions

- 批次上限十筆是否符合實際策展節奏，或應依快照總位元組數動態決定。留待實際使用回饋後調整。
- 是否需要跨頁掃描 Ready for dev。需先確認載入所有頁面在大型檔案的耗時是否可接受，屬後續獨立變更。
