## Context

外掛匯入文字節點時，依 CSS 家族堆疊逐一嘗試載入字型：每個家族先試歐文候選 style，全數失敗再查該家族實際可用的 style 清單並以最近字重挑選，仍失敗才換下一個家族，最後保底為 Inter Regular。這套解析由 requirement「Text style application」定義，行為正確且已有純函式測試覆蓋。

問題出在解析結果的回報。匯入統計目前只有 `warnings` 這個字串陣列，字型替換與所有其他警告共用同一通道；外掛 UI 把它渲染成高度上限 88px 的可捲動小字區。四個文字節點被替換時會產生 8 條訊息，與其他警告混在一起，使用者不會意識到「這次匯入的字型全被換掉了」。

2026-07-29 的案例顯示這個回報缺口的代價：Figma 本機字型檔服務連線被拒，所有系統字型載入失敗，四個節點全部替換成 Noto 系列。使用者看到匯入成功且畫面近似，判定正常；實際字型是後續以 Figma MCP 讀取節點才確認。診斷根因則必須依賴瀏覽器 console 的網路錯誤，因為外掛訊息只說某個家族不可用，未能表達「所有本機字型都載不到」這個全域態樣。

約束：外掛在 Figma plugin sandbox 內執行，無法直接探測本機字型服務的連線狀態，只能從自身的載入結果推論。純函式為主要可測單元，既有測試在 `test/verify-pure-functions.cjs`；`code.js` 由 `code.ts` 建置產生，`storybook-template` 下有一份僅收 runtime 檔案的鏡像需保持一致。

## Goals / Non-Goals

### Goals

- 讓字型替換在匯入完成時即可被察覺，不需事後以外部工具檢查節點。
- 讓替換紀錄足以支撐診斷：知道請求什麼、實際得到什麼、嘗試過哪些 style。
- 區分「個別字型不可用」與「本機字型環境整體不可用」，使回報指向正確的處置方向。

### Non-Goals

- 不變更字型解析邏輯、候選次序或 Inter Regular 保底。
- 不阻擋或中止發生替換的匯入，替換仍是可接受的降級行為。
- 不新增自動重試、字型安裝或連線修復。
- 不變更匯出端 addon 與 payload schema。
- 不處理舊 `sbfx-json-importer` fork 副本。

## Decisions

### 決策一：以結構化替換紀錄取代純字串警告

匯入統計新增字型替換清單，每筆為結構化紀錄，欄位涵蓋節點路徑、請求家族、請求字重、實際家族、實際 style，以及該次嘗試過的全部 style 名稱。原有的 `warnings` 字串維持不變以確保相容。

理由：字串訊息無法被 UI 或後續工具可靠解析，也無法計數。要讓 UI 在摘要層級顯示替換次數、要讓紀錄支撐診斷，就必須有結構化欄位。

替代方案是「維持字串，改以前綴標記字型警告再由 UI 過濾」。否決原因是前綴解析脆弱，訊息一改就失效，且無法承載嘗試過的 style 清單這類結構化資料。

### 決策二：以「兩個以上不同家族全部載入失敗」判定環境異常

同一次匯入中，若有兩個以上**不同**的字型家族其所有 style 皆載入失敗，判定為本機字型環境異常，回報改為說明所有本機字型皆無法載入，並建議重啟 Figma 或檢查字型存取權限。僅單一家族失敗時不做此判定，維持既有的個別字型訊息。

理由：外掛在 sandbox 內無法探測字型服務連線，只能從載入結果推論。單一家族失敗的常見原因是該字型未安裝，屬正常情況；兩個以上不相關家族同時全滅則難以用「剛好都沒裝」解釋，指向共同的環境因素。實測案例正是兩個家族（Hiragino Kaku Gothic ProN、Hiragino Mincho ProN）同時失敗。

替代方案一是「任何一次失敗都提示可能是環境問題」。否決原因是會對「單純沒裝這個字型」這種正常情況產生假警報，降低訊息可信度。

替代方案二是「由外掛主動探測字型服務端點」。否決原因是 plugin sandbox 不允許任意網路存取，且端點與埠號屬 Figma 內部實作，依賴它會使外掛與未公開行為耦合。

門檻定為 2 而非更高，是因為多數 story 只用到一到兩個家族；門檻若設為 3，實測案例這種兩個家族全滅的情況就不會被判定，缺口依舊。

### 決策三：嘗試過的 style 由解析路徑回傳，而非於警告處重建

available-style 解析階段實際嘗試的 style 名稱，由解析函式一併回傳給呼叫端，再寫入替換紀錄；警告文字不再自行拼裝解析前的候選清單。

理由：現行訊息只列得出解析前的歐文候選，因為警告是在解析函式外部產生的，看不到函式內部查到並嘗試過的 W-number style。這正是該次診斷無法從外掛回報判斷「W6 是否被嘗試過」的原因。

### 決策四：UI 摘要顯示替換次數，不使用阻擋式提示

替換次數顯示在既有摘要行，與節點數、變數數同層級。不新增彈窗、不阻擋流程。

理由：替換是降級而非錯誤，阻擋會妨礙正常工作流。但它必須脫離需要捲動才看得到的細節區，才具備被察覺的機會。

## Implementation Contract

### 可觀察行為

- 匯入未發生任何字型替換時，統計中的替換清單為空，UI 摘要不顯示替換相關文字。
- 每個字型遭替換的文字節點，在統計的替換清單中各產生一筆紀錄，內容包含節點路徑、請求家族、請求字重、實際載入的家族與 style，以及該次嘗試過的全部 style 名稱。
- 嘗試過的 style 名稱包含 available-style 解析階段實際嘗試的 style；當該階段查到 W-number style 並嘗試載入時，該名稱出現在紀錄中。
- 同一次匯入中兩個以上不同家族的所有 style 皆載入失敗時，回報包含本機字型環境異常的判定，以及重啟 Figma 或檢查字型存取權限的建議。僅一個家族失敗時不出現該判定。
- UI 摘要於替換次數大於零時顯示該次數。

### 介面

環境異常判定需為不依賴 Figma runtime API 的純函式，輸入為本次匯入的字型替換紀錄集合，輸出為是否判定環境異常及涉及的家族名稱清單。純函式不得呼叫 Figma API。

### 失敗模式

替換紀錄的收集與環境異常判定皆不得拋出例外中止匯入。任何欄位缺漏時以空值記錄，匯入流程繼續。

### 驗收

- `test/verify-pure-functions.cjs` 新增案例涵蓋：零替換、單一家族失敗不判定環境異常、兩個家族失敗判定環境異常、紀錄含 available-style 階段嘗試的 style 名稱。
- `node test/verify-pure-functions.cjs`、`node test/verify-manifest.mjs`、`node test/verify-bridge-helpers.cjs` 全數通過。
- 外掛目錄 `npm run build` 通過型別檢查。

### 範圍邊界

在範圍內：`code.ts` 的字型載入回報路徑與匯入統計欄位、`ui.html` 的摘要顯示、純函式測試、外掛版本號、`storybook-template` 的 runtime 鏡像（`code.js`、`ui.html`、`manifest.json`、`README.md`，不得放入 `code.ts`、`package.json`、測試或建置設定）。

在範圍外：字型解析邏輯與候選次序、匯出端 addon、payload schema、`page` 匯入路徑、variant 組選擇、舊 `sbfx-json-importer` fork 副本。
