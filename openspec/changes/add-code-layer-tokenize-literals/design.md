## Context

Code Layer 1.1.0（add-storybook-code-layer）的寫入只有一種形狀：把 `var()` 裡的 token 名稱換成另一個既有的 token。值是寫死的分量在追蹤結果裡是 `raw`，檢視器顯示為唯讀，原因是 `raw-value`。

現況中與這個 change 有關的事實（2026-11-25 讀碼與實測）：

- 索引已經把每個宣告的值拆成最上層的分量（`shared/value-refs.mjs` 的 `splitTopLevel`、`classifyValue`），每個分量有文字、形狀（`single-var`、`raw`、`keyword`、`expression`、`separator`）與在值裡的位置。追蹤時每個 slot（邏輯 longhand）對到「哪個宣告的第幾個分量」。所以「`margin: 0 0 var(--gap)` 的上邊是第 0 個分量、寫死的 `0`」這件事已經算得出來。
- 寫入的證明在 `server/patcher.mjs`：每筆編輯是一段位元組區間，證明新檔等於舊檔把這些區間換成預期的位元組，再重新解析比對節點序列。區間目前只會是 token 名稱。
- 即時預覽把同一個宣告上的草稿依序套在索引給的原始值上，再整段 `setProperty`。probe 則是在 CSSOM 序列化後的值上以「第幾個 `var()`」替換哨兵值。
- 反向套用（`server/transaction.mjs` 的 `reverse`）由 journal 的操作紀錄建立反向操作，再走一般的 `runBatch`，所以反向操作要通過與請求相同的 `validateBatch`。
- 檢視器的屬性表（哪些 slot、每個 slot 接受哪些型別的 token）在 `shared/properties.ts`，伺服器讀不到 TypeScript 檔。伺服器目前只檢查「新舊 token 型別相容」。
- 試驗場的實測數字見 proposal。量測用的腳本只讀檔，沒有保留在 repo。

使用者已定案的方向不變：以改綁既有 token 為主、不自己發明數值；先暫存再套用；預設改元件本身；專案的 system tier 維持關閉；工具介面用 Storybook 的主題。

## Goals / Non-Goals

**Goals:**

- 檢視器上寫死的值，只要有型別相符的既有 token，就能換成 token，手感與改綁相同（點開、挑選、即時預覽、套用、還原）。
- 寫死的數值剛好等於某個 token 時，一眼看得出來，換了之後工具明確回報外觀沒變。
- 1.1.0 的安全性質全部保留：封閉可寫集合、位元組級最小差異、拒絕時零寫入、可還原、驗證不自我證明、請求不能提供要寫入的文字。
- 仍然鎖住的值都說得出原因。

**Non-Goals:**

- 把寫死的數值改成另一個寫死的數值（例如 `70%` 改成 `80%`）。這是「自己發明數值」，維持不做。
- 新增 token（包含「把這個數值抽成一個新的 component token」）。命名與層級需要人決定，屬於 agent lane。
- 關鍵字（`auto`、`bold`、`normal`、`currentcolor`）、函式與運算式（`calc()`、`min()`）、以逗號或斜線分隔的值（字體清單、橢圓圓角）。
- token 檔裡值是寫死的 component token。試驗場 102 個 component token 全部是單一 alias，沒有這種情況；有需要時另案處理。
- 版面結構的編輯（display、方向、對齊、換行）。這是候選功能 B。
- 依數值相同自動批次替換整個專案。每一筆都由人在檢視器上選。
- 改變既有改綁操作的驗證語意。換成數值相同的 token 的改綁，仍然回報「此頁看不到效果」。

## Decisions

### 可以換成 token 的字面值是值的最上層、以空白分隔的一個分量

一個分量可以換成 token，必須同時成立：

1. 宣告是該列的勝出宣告，所在樣式表通過身分檢查而且可寫；宣告不是 `!important`、在規則內沒有重複、沒有被同規則後面的宣告蓋掉（與改綁相同的條件）。
2. 值的最上層沒有逗號或斜線。
3. 該分量不含 `var()`，不是關鍵字，`inferKind` 判定為顏色、長度、百分比、數字、零或單一字體。
4. 這個型別是該列所屬屬性接受的型別（屬性表的 `kinds`）。
5. 該宣告可以引用的 token 當中，至少有一個的型別是該屬性接受的型別。

不符合時維持唯讀，原因分別是：關鍵字 `keyword`（既有）、函式或無法辨識的值 `literal-expression`、有逗號或斜線 `literal-list`、沒有型別相符的 token `no-token-of-kind`。原本的 `raw-value` 不再出現在可辨識的字面值上。

值本身的形狀可以是 `raw`（完全沒有引用）或 `var-list`（引用與字面值混合）。分量以它在最上層分量清單中的位置定址。因為第 2 條排除了分隔符號，這個位置在替換前後不會變。

替代方案「只支援整個值就是一個字面值」比較簡單，但 `margin: 0 0 var(--gap)`、`border: 1px solid #000` 這類簡寫會繼續鎖住，而它們正是最常見的情況。

### 候選是屬性接受的型別，依數值相同、這個屬性用過的類別、其他類別排序

候選 = 可以當改綁目標的 token（`isRebindTarget`）∩ 宣告範圍的層級規則（system token，或同一個元件的 component token）∩ 型別在屬性表的 `kinds` 之內。

型別規則用「屬性接受的型別」，不用「與字面值相同的型別」。字面值沒有舊 token 可以對照，而 `max-inline-size: 100%` 換成一個固定尺寸的 token 是合理的設計決定。採用後者的話，試驗場 7 個百分比尺寸會因為專案沒有百分比 token 而繼續鎖住。

排序分三組：

1. **數值相同**：屬於「這個屬性用過的類別」，而且在目前主題下的解析值等於字面值。標示「數值相同」。
2. **這個屬性用過的類別**的其餘 token。數值可以比較時（同單位的長度、數字、百分比）依與字面值的差距由近到遠，否則依名稱。
3. **其他類別**，依名稱。數值相同的仍然標示，但不會排到前面。

「這個屬性用過的類別」由索引算出，不靠命名猜：掃過專案所有元件樣式表，每個屬性群組（padding、margin、fill…）已經引用的 token 沿 alias 走到 system token，取它名稱中的類別段（`spacing`、`shape`、`color`、`typescale`）。某個群組一次都沒用過時，取同一個檢視器區段其他群組用過的類別（試驗場的 `max-inline-size` 因此取得 `size`）。component token 的類別是它所 alias 的 system token 的類別。

這條規則的理由是試驗場的實測：9 個 `margin: 0` 唯一數值相同的 token 是 `--md-sys-shape-corner-none`，它是圓角 token。只看數值會把它排在第一位。

「數值相同」的定義（`shared/literals.mjs`，伺服器不使用）：同一個顏色（正規化後相同）；或同一個數字而且單位相同；或兩者都是零。`1em` 與 `16px` 不算相同，因為換到別的元素上結果不同。比較用 preview 回報的目前主題的值，沒有時用索引的靜態值。

### 操作 tokenize-literal 以分量位置定址，伺服器自己驗證型別

```jsonc
{ "id": "op-1", "type": "tokenize-literal",
  "file": "src/components/ribbon-banner/RibbonBanner.css",
  "rule": { "ordinal": 0, "selector": ".md-ribbon-banner", "atRules": [], "occurrence": 0 },
  "declaration": { "property": "margin" },
  "component": 0,
  "literal": "0",
  "toToken": "--md-sys-spacing-stack-gap-sm",
  "before": { "value": "0" },
  "after":  { "value": "var(--md-sys-spacing-stack-gap-sm)" } }
```

伺服器依序檢查：

- 檔案、規則、宣告的定位，以及 `!important`、規則內重複、被蓋掉，與 `rebind-declaration` 相同。
- 宣告的形狀是 `raw` 或 `var-list`，最上層沒有分隔符號；第 `component` 個分量是 `raw`、文字等於 `literal`；宣告的值等於 `before.value`（否則 `stale-before`）。
- 目標 token 存在於 tier 檔、只宣告一次、解析得出值；是 system token 或同元件的 component token（否則 `tier-rule`、`foreign-comp-token`）。
- 型別：伺服器以 `sidesOf` 在所有支援的書寫方向下算出這個分量設定的 slot，每個 slot 都必須在屬性表內，而且目標 token 的型別必須被每個 slot 接受（否則 `type-mismatch`）。屬性不在表內為 `unsupported-value-shape`。
- 新值由伺服器算出，必須等於 `after.value`。

請求裡的 `literal` 只用來比對現況，不會被寫入。伺服器寫進檔案的位元組只有 `var(`、索引中的 token 名稱、`)`。

型別檢查放在伺服器的理由：改綁靠「新舊 token 型別相容」當防線，字面值沒有舊 token。不檢查的話，零值 `0` 與任何數值型別都相容，請求可以把 `margin: 0` 換成一個沒有單位的數字 token，瀏覽器會丟掉整個宣告。

### 位元組證明從 token 名稱擴大為一個分量

`patcher.mjs` 的編輯分成兩種：名稱編輯（既有）與分量編輯。分量編輯的區間是該分量在宣告原始值中的起訖位置（`splitTopLevel` 在遮掉註解與字串後計算，所以緊鄰的註解不在區間內），替換成 `var(--名稱)`。

兩道證明不變，只是把「舊名稱／新名稱」一般化為「舊文字／新文字」：

1. 位元組：新檔等於舊檔把已知區間換成預期位元組，其餘各段逐位元組相同。
2. 重新解析：節點序列相同，未被定址的宣告原始值不變，被定址的宣告等於預期的新值。

第二道證明同時擋下任何會改變結構的文字：替換後多出或少掉一個節點就失敗。

### 同一個宣告上的改綁與換 token 可以同批

把字面值換成 `var()` 會在值裡多一個引用，後面的引用在「第幾個 `var()`」的編號會往後移。分量位置不會移。因此：

- 伺服器：同一批的所有操作都對同一份讀檔結果定位，各自產生不重疊的位元組區間，由後往前套用。順序不影響結果。
- 即時預覽：同一個宣告上先套改綁（以引用編號），再套換 token（以分量位置）。
- journal：每筆宣告操作多記一個 `component`（分量位置）。反向套用找引用時優先用它，沒有這個欄位的舊紀錄才用引用編號。

替代方案「同一個宣告上不能同批」實作最少，但設計師會遇到無法理解的拒絕。

### 反向套用寫回伺服器自己記下的字面值

整檔還原（備份寫回）不變。反向套用時，`tokenize-literal` 的反向是內部操作 `restore-literal`：把第 `component` 個分量由 `var(--當初寫入的 token)` 換回 journal 記下的字面值。

- journal 的字面值是套用當下伺服器從檔案讀到、並與索引比對過的文字，不是請求提供的。
- `restore-literal` 只由 `reverse` 建立。來自 HTTP 的批次含有這個型別時以 `schema-invalid` 拒絕。
- 該分量現在不是「恰好一個、沒有 fallback 的 `var(--那個 token)`」時，以 `stale-before` 拒絕。
- 寫回前再驗一次：字面值重新分類後必須是單一的 `raw` 分量；位元組與重新解析兩道證明照常。

這樣「請求不能提供要寫入的文字」仍然成立：唯一會寫入字面文字的路徑，寫的是那個位置原本就有、由伺服器記錄的文字。

### 驗證多一種結果：已驗證、外觀不變

1.1.0 的規則是「預覽開與關的值不同，才叫已驗證」，預覽沒有改變任何值時歸為「已寫入，此頁看不到效果」。換成數值相同的 token 是這項功能的主要用途之一，它的預期結果正是外觀不變，歸到「看不到效果」會讓人以為沒有成功。

新增第五種結果 `verified-same`，只用於 `tokenize-literal`，條件是：

- 第一層通過：頁面樣式表的文字等於伺服器回報寫入的內容。
- 見證元素在這一頁；套用前量到的 A（預覽全關）與 B（預覽全開）相同。
- 寫入後、移除預覽再量到的 C 等於 A。

這個結果宣稱的是「檔案已經是新內容，而且外觀沒有變」，兩件事都有不依賴預覽的證據。至於「這個宣告確實作用在這個元素上」，由選擇器開啟前的 probe 證明：probe 沒有確認的列不能選。

其他情況不變：見證元素不在這一頁仍是「此頁看不到效果」，C 與 B 不同是「不符」。

### 預覽與 probe 用原始碼的值替換分量

CSSOM 會把沒有 `var()` 的值正規化（`margin: 8px 8px` 讀回來是 `8px`，`#FFF` 讀回來是 `rgb(255, 255, 255)`），所以不能在 CSSOM 讀回的值上數「第幾個分量」。

- 預覽：以索引給的原始值為基底，用與伺服器相同的函式（`shared/literals.mjs` 的 `replaceComponent`）替換後整段 `setProperty`，優先權沿用原宣告。
- probe：同樣以索引的原始值為基底，把該分量換成哨兵值後整段寫入，量完寫回 CSSOM 原本的文字；既有的「規則文字前後相同，否則由樣式表自己的文字重建」保護照用。
- 草稿的分類不讀 CSSOM，做法與改綁相同：頁面樣式表文字的雜湊先要等於索引的雜湊，再由索引中該分量現在的內容決定——仍是原本的字面值為尚未寫入，已經是 `var(--選的 token)` 為已寫入，其他為衝突。

### 檢視器上的呈現

- 寫死值的列：顯示數值，token 的位置是一個「未綁定」的記號，整列可以點（不再是鎖頭）。tooltip 是「寫死的數值，可以換成 token」。
- 點開是同一個選擇器，最上面一行是目前的字面值。候選依三組排列，數值相同的有標示。滑過即預覽、選了才暫存，與改綁相同。
- 這種列只有「宣告」一個範圍，不顯示範圍切換。
- 暫存後，列上顯示選的 token 與原本的字面值。變更清單的一行是「字面值 → token」。
- 這種列不提供逐級調整（方向鍵、拖曳、步進鈕），因為沒有目前的 token 可以當起點。套用之後它就是一般的 token 列。
- 報告：`verified-same` 顯示為「已寫入並驗證，外觀不變」。
- 所有新字串加進 `messages.zh-Hant.ts` 與 `messages.en.ts`。

### 文件待同步只記宣告本身

每筆 `tokenize-literal` 產生一條 `declaration-not-documented`（與 `rebind-declaration` 相同：元件樣式表的宣告沒有對應的規格表），同一行有註解時另記一條。

不做「搜尋文件中提到舊值的地方」。改綁搜尋的是舊 token 的短名，它是一個名稱；字面值 `0`、`8px`、`100%` 會命中大量無關的行。

換 token 不會動到 token 檔，所以不重寫 Token Contract 的列，也不跑 token 檢查；配對色檢查（只看 component token 的改綁）不適用。

### 屬性表改成伺服器與瀏覽器共用

`shared/properties.ts` 的 `GROUPS` 資料移到 `shared/property-table.mjs`（純資料加 `.d.mts`），`properties.ts` 改為匯入後加上型別再匯出，行為不變。伺服器從同一份表取得每個 slot 接受的型別。

替代方案「在伺服器另寫一份 slot 對型別的表」會有兩份定義，日後新增屬性時容易只改一邊。

## Risks / Trade-offs

- **換了不同數值的 token，外觀會變，而且影響所有套用同一條規則的元素** → 與改綁相同：列上與變更清單顯示寫入位置與影響的宣告數，暫存期間只是預覽，套用後可以還原。
- **「數值相同」只對目前的主題成立**：token 在另一個主題下可以有不同的值，寫死的值不會 → 標示用目前主題的值計算；切換主題時重新計算。README 與說明文件寫明這一點。
- **類別排序依賴專案既有的用法**：完全沒有用過 token 的屬性，在同區段也沒有用法時，沒有前兩組，所有候選依名稱排列 → 仍然可用，只是沒有建議順序。
- **寫入端點的能力範圍略為擴大**（見 proposal 的 Impact）→ 仍然限於封閉可寫集合、既有 token、型別相符，每一筆可還原；請求不能提供文字。
- **反向套用信任 journal 裡的字面值**：能改 journal 的人已經能改專案的任何檔 → 寫回前仍重新分類字面值並跑兩道證明，結構改變就失敗。
- **`inferKind` 對不認得的具名顏色判為關鍵字**（只認得常見的 19 個）→ 這種值維持唯讀，原因是關鍵字；不會被誤換。
- **1.1.0 的 journal 沒有分量位置** → 反向套用對舊紀錄沿用引用編號，行為與 1.1.0 相同。

## Migration Plan

1. 模板版本 1.2.0，`KNOWN_MANIFESTS.json` 加入 1.2.0。
2. 既有專案以 `install_code_layer.mjs --update` 升級；專案綁定不需要修改。
3. 試驗場升級時依既有安排由我停掉並重啟 6006 上的 Storybook，升級前先記錄一份新的雜湊基準（試驗場現在有使用者自己的兩筆套用）。
4. 回復方式：以安裝器裝回 1.1.0 的模板。已經用 1.2.0 套用的換 token 仍可用整檔還原（備份）取消；1.1.0 不認得這種操作的反向套用。
