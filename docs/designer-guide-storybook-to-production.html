Route A

路線 A：原型 → 產品

當你做的是一個完整功能——有多個畫面、有流程、需要團隊共識——走這條。原型階段產出的交接文件，就是 AI 在產品端的施工圖。

適合：新功能、新頁面組、需要 PM 與工程一起確認的東西。
  1. 1

    確認交接包完整

    在原型專案的 docs/ 資料夾裡有七份文件。你只需重點看 PRODUCTION_HANDOFF.md：目標頁面寫對了嗎？哪些狀態（載入中、錯誤、空白）要做？沒把握就請 AI 唸給你聽。

    幫我檢查這個原型的交接文件是否完整，用白話總結 PRODUCTION_HANDOFF 給我聽。
  2. 2

    到產品專案，說一句話

    切換到正式產品的專案，告訴 AI 依交接文件實作。它會自動判斷產品用什麼框架，不會把技術選擇丟回來問你。

    請用 frontend-product-implementation，依原型的 handoff 文件把這個功能實作進產品。
  3. 3

    AI 先盤點，再動工

    動工前 AI 會先掃一遍產品：有哪些 tokens、哪些現成元件、文字放在哪裡管理。原則是「先用現成的」，拼不出來才會問你要不要新增。真實 API 和資料先用假資料代替，等工程師接手。

  4. 4

    回答核准問題

    如果產品缺 tokens 或缺元件，AI 會停下來問你——下面「三個紅綠燈」有每一題的模擬對話，可以先看過一遍心裡有底。

  5. 5

    驗收

    請 AI 把做好的產品畫面和 Storybook 原型比一輪，它會附上截圖證據，跑版就修。

    請用 ui-compare-to-reference，以 Storybook 原型為準比對產品畫面並修正差異。
Route B

路線 B：元件庫 → 直接組裝

當你只是要加一個畫面、改一個版，設計稿已經很明確，不需要整套 PRD 和原型——直接用 Storybook 元件庫當積木，請 AI 在產品裡拼出來。

適合：單一畫面、既有頁面改版、設計稿（Figma 或截圖）已定案的小需求。
  1. 1

    準備一份參考

    一個 Figma 連結、一張設計稿截圖、或一段清楚的描述，三者擇一。這就是 AI 的施工依據。

  2. 2

    選對入口

    有截圖或設計稿 → 請 AI 先「認積木」：它會盤點畫面上有哪些元件、對應到元件庫的哪些現成件、缺哪些。只有文字需求 → 直接請 AI 實作。

    （有設計稿）請用 ui-screenshot-to-storybook-product，用我們的元件庫實作這張設計稿。
    （只有需求）請用 frontend-product-implementation，在產品的〇〇頁面加上〇〇功能，元件請用我們 Storybook 裡現成的。
  3. 3

    AI 用現成元件拼裝

    和路線 A 一樣，AI 會先盤點元件庫再動工，不會為了一張稿另起爐灶做重複的按鈕。畫面上的顏色間距全部走 tokens，不寫死。

  4. 4

    回答核准問題，然後驗收

    缺 token、缺元件一樣會先問你。完成後請 AI 出一份像素比對報告，以你的設計稿為準。

    請用 ui-pixel-align-report，以這張設計稿為準，產出產品畫面的像素比對報告。

一句話判斷：需要「說服別人或驗證想法」→ 路線 A；只是「把定案的東西做出來」→ 路線 B。中途發現 B 越做越大，隨時可以回頭補原型和文件，兩條路不衝突。

Approval Gates

三個紅綠燈：AI 何時會停下來等你

不管走哪條路線，遇到這三種情況 AI 都會停下來問你，不會自作主張。展開「看模擬對話」，先預覽 AI 會怎麼問、你可以怎麼回——實際遇到時就不會慌。

GATE 1

產品裡沒有 design tokens

AI 會啟動「token 搬運計畫」：從你的 Storybook 元件庫找出這次實際用到的顏色、字級、間距，列成一張最小清單給你看，並依產品的技術選好落地格式。你點頭，它才建立。不會整包硬搬，也不會偷偷寫死數值。

看模擬對話
這個產品專案裡找不到 design token 系統。我建議建立一組最小 token——這次畫面實際用到的 9 個（sys-color-primary、sys-spacing-md⋯⋯每個都對應到你 Storybook 元件庫的來源檔案）。落地格式建議用 CSS variables，因為這個產品是純 CSS。要建立嗎？
你可以這樣回可以，照清單建立先列出這 9 個給我看等等，我找工程師確認格式
GATE 2

現成元件拼不出這個畫面

AI 會告訴你缺哪塊積木，問你要不要先做一個新的共用元件。你同意後它才建，並且會同步補上 Storybook 文件——新積木從此進元件庫，下次直接用。

看模擬對話
這張畫面需要一個「可搜尋的下拉選單」，但元件庫目前只有基本的 Select。兩個選項：（1）建立新的共用元件 SearchableSelect，會一併補上 Storybook 文件；（2）先用現有 Select 頂著，搜尋功能之後再加。你想走哪個？
你可以這樣回建立新元件先用現有 Select給我看兩種的畫面差異
GATE 3

產品的樣式寫法不只一種

老專案常常混用多種樣式技術。AI 分不出哪個是主流時，會列出選項問你（或問工程師）要走哪一套，確定了才動工，避免把新畫面蓋在錯的地基上。

看模擬對話
這個專案同時存在 SCSS variables 和 CSS custom properties 兩套寫法，各佔約一半，判斷不出主流。新建立的 tokens 要走哪一套？
你可以這樣回我問一下工程師再回你先列出兩套各用在哪些地方
BACKUP

連 Storybook 端都沒有 tokens？

最壞情況也有備案：AI 會從你的設計稿和原型樣式「逆向整理」出一份候選 token 表——每個值都附出處——先交給你核准，才開始建。永遠不會發生「沒有 tokens 所以先寫死」這件事。

Cheat Sheet

名詞小抄

流程中會出現的詞，用設計師的語言翻譯一次。

Design Token
設計決策的最小單位：一個顏色、一個字級、一個間距，都有名字。改一個 token，全產品跟著改——這就是為什麼絕不寫死數值。
元件庫（Component Library）
Storybook 裡那些有文件、可重用的積木：按鈕、輸入框、卡片。產品畫面應該用積木拼，而不是每頁重畫。
Handoff（交接文件）
原型階段產出的七份文件，讓接手的人不用私訊問你「這裡是什麼意思」。核心是 PRODUCTION_HANDOFF.md。
UI Flow
畫面與畫面之間怎麼跳轉的地圖：從哪裡點什麼、到哪裡去，包含錯誤和載入這些中途狀態。
Fixture（假資料）
寫死的示範資料，讓畫面在真實 API 接上之前就能完整展示。工程師之後把它換成真資料，畫面不用重做。
ref → sys → comp
token 的三層命名：ref 是原料（藍色 500），sys 是語意（主色），comp 是元件用途（按鈕底色）。搬運 tokens 時這個層級會被完整保留。
